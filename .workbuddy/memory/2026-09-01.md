## 修复 `_parse_pod_name` 解析 bug（sched-failpod 被解析为 Pending）

- **症状**：`curl /diagnose` 问 "defualt命名空间的sched-failpod 一直 Pending"，返回 `Pod default/Pending not found`，problem 永远是 CrashLoopBackOff，与 API Key 无关。
- **根因**：`_parse_pod_name` 只取纯 ASCII 单词（`split()` + `isascii()`），中文+英文连写（`空间的sched-failpod`）被整词丢弃；fallback 取第一个 ASCII 词，把状态描述词 `Pending` 当成了 pod 名。
- **修复**（`src/infrastructure_agent/workflow/pod_crash_workflow.py`）：
  - `_POD_TOKEN_RE = re.compile(r"[a-z0-9][a-z0-9-]*[a-z0-9]")` 从任意文本中提取 k8s 标识符（含中文混合词）；
  - `_STATUS_WORDS` 排除 pending/running/crashloopbackoff 等状态词 + 命名空间词 + 结构词（pod/service/ns...）；
  - 优先级：含 `-` 的 token > 已知前缀（nginx/app/web/sched/test...）> fallback "nginx"；
  - `_parse_namespace` 支持 `xxx命名空间/namespace/ns` 显式上下文 + `_NAMESPACE_ALIASES` 别名表。
- **验证**：11 个用例全部通过（含历史 5 场景 + 本次报错输入）；mock 模式端到端 diagnose 无回归。
- **注意**：服务需重启才能生效；真实集群上 sched-failpod 存在，应返回 FailedScheduling 而非 CrashLoopBackOff。

## 修复 LLM 静默降级问题（sched-failpod 场景 LLM 不参与分析）

- **症状**：reasoning_trace 最后一步是 "All evidence collected: ..."（rule fallback 专属格式），API Key 配置正确但 LLM 未生效。
- **根因链**（3 个静默失败点，逐层排查）：
  1. `rca_node` 返回 `_rca_mode`（下划线开头）→ Pydantic v2 私有字段，被丢弃，响应里看不到 LLM 是否参与；
  2. `llm/client.py generate()` 的 `except Exception: return None` 吞掉所有调用异常，无日志；
  3. **真正原因**：`rca_node` 的 `max_tokens=800` 对中文长 RCA 偏小，证据不足时 LLM 话痨输出被截断 → JSON 不完整 → `generate_structured` 静默 fallback。
- **修复**：
  - `WorkflowState` 增加公开字段 `rca_mode`（llm/rule/unknown/error），API 响应透出 → 一眼可判断 LLM 是否参与；
  - `generate()` 异常打 warning 日志（含 model/base_url/异常类型）；
  - `generate_structured()` JSON 解析失败时尝试 `_extract_json_object()`（brace 深度扫描提取首个 {...}），仍失败则打 warning 日志；
  - `get_llm_client()` 单例缓存空 key 时自动重建（改 .env 后无需重启进程）；
  - `rca_node` max_tokens 800 → 1500。
- **验证**：sched-failpod 场景 rca_mode 从 rule → llm；nginx-oom 场景保持 llm。
- **经验**：中文 LLM 输出的 max_tokens 保守给 1500+；所有 LLM 降级路径必须可观测（日志 + 响应字段），禁止静默吞异常。
