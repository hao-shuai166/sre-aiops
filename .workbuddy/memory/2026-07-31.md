## RCA 诊断质量修复（4 项修改）

**问题**：用户测试真实 nginx CrashLoopBackOff Pod，诊断结果为 "应用启动异常"（过于模糊，实质是重述症状），confidence 0.6 偏高。

**根因分析**：
1. `_get_pod_real()` 只查 `cs.state.terminated` 取 exit_code，CrashLoopBackOff 时当前 state 是 waiting，退出码在 `lastState.terminated` 中 → exit_code 始终为 null
2. `query_app_logs` 空日志 → 推理结论 "日志中无明显错误" → 掩盖了 "容器启动即崩溃无输出" 这个强信号
3. `_fallback_rca` 空日志分支无 exit_code 分析，统一归为 "应用启动异常"

**修改内容**：
1. **k8s_client.py** — `_get_pod_real()` 新增 `cs.last_state.terminated` 检查，提取 last_exit_code / last_reason / last_message
2. **evidence_builder.py** — `build_from_get_pod()` 从 containers info 中提取 lastState 字段到 evidence content 顶层
3. **pod_crash_workflow.py query_app_logs** — 空日志推理改为 "容器启动即崩溃，未产生日志——需检查 entrypoint、启动命令及 exit_code"，区分空日志/有错误日志/无错误日志三种情况
4. **pod_crash_workflow.py _fallback_rca** — 空日志分支按 exit_code 值分路径：137(OOM) / 1(应用异常) / 126(无权限) / 127(命令未找到) / 未知(低 confidence 0.35)

**测试**：5/5 mock 场景通过

## ImagePullBackOff Pod 查询 500 错误修复

**问题**：查询 ImagePullBackOff 状态的 Pod 时报 `TypeError: '<' not supported between instances of 'datetime.datetime' and 'str'`，根因是 `_get_events_real()` 中 `sorted(..., key=lambda e: e.last_timestamp or "")`，当 last_timestamp 为 None 时 fallback 到 `""`（字符串），与 datetime 对象无法比较。

**修复**：`k8s_client.py` line 382，`""` → `datetime.min`

## ImagePullBackOff Pod 第二个 500 错误修复 + 两项改进

**问题**：ImagePullBackOff Pod 查询仍报 TypeError: `can't compare offset-naive and offset-aware datetimes`。上次修复用 `datetime.min` 替换了空字符串，但 `datetime.min` 是 offset-naive，K8s `last_timestamp` 是 offset-aware，类型仍不兼容。

**修复**：`datetime.min` → `datetime.min.replace(tzinfo=timezone.utc)`

**改进 1 — Problem 字段动态化**：
- 新增 `_EVENT_ROUTE_PROBLEM_MAP` + `_diagnosis_problem()` 辅助函数
- 根据 `classify_event` 的路由结果输出对应的 problem 名称（如 "Pod ImagePullBackOff" / "Pod OOMKilled" / "Pod FailedScheduling"）
- `_fallback_rca` 和 `rca_node` 两处不再硬编码 "Pod CrashLoopBackOff"

**改进 2 — API 层全局异常捕获**：
- `_run_pod_diagnosis` 中 `graph.ainvoke` 包裹 try/except，捕获后返回结构化错误（problem: "diagnosis_error" + 异常信息）
- `diagnose_endpoint` 增加兜底 try/except，即使 diagnose() 抛出未预期的异常也返回 DiagnoseResponse 而非裸 500

**测试**：5/5 mock 场景通过

## classify_event 路由逻辑修复（两轮）

### 第一轮：只查 reason 不查 message
K8s Event `reason="Failed"`, `message="Error: ImagePullBackOff"`。只拼 reason 匹配不到。
修复：同时拼接 reason + message。

### 第二轮：Events 过期后只剩 BackOff，PodStatus 未被检查
K8s Events API 只返回最近一条 `reason="BackOff"`, `message="Back-off pulling image"` — 既没有 "imagepullbackoff" 也没有 "errimagepull"。但 PodStatus evidence 里 `containers[0].reason = "ImagePullBackOff"` 才是最权威的信号。

修复：`classify_event` 改为两级检查：
1. **先查 PodStatus** — 容器 waiting reason 是最可靠的（ImagePullBackOff / OOMKilled / CreateContainerConfigError）
2. **再查 KubernetesEvent** — reason + message 拼接做关键词匹配，新增 "back-off pulling image" / "failed to pull image" 等 message 模式

**测试**：5/5 mock 场景通过

## Events field_selector 精确化

`_get_events_real` 的 field_selector 只过滤了 `involvedObject.name`，没过滤 `involvedObject.kind`。如果命名空间里有同名 Service/ConfigMap，其事件会混入。

修复：`field_selector` 增加 `involvedObject.kind=Pod`。

**测试**：5/5 mock 场景通过

## _fallback_rca 只查 reason 不查 message 导致 root_cause=Unknown

classify_event 修好后正确路由到 image_pull，但 `_fallback_rca` 仍只检查 events 的 `reason` 字段（"BackOff"/"Failed"/"Pulling"），不检查 `message`。ImagePullBackOff 场景下匹配不到 "imagepullbackoff" → root_cause 保持 "Unknown"。

修复：
1. `_fallback_rca` 改为 reason + message 联合匹配（同 classify_event）
2. 新增 `"failed to pull image"` / `"back-off pulling image"` 等 message 模式
3. 新增 `_extract_image_from_events()` 辅助函数，从 message 中提取镜像名用于诊断
4. image_pull 细分：镜像不存在（"not found"）vs 其他拉取失败

## decision_node 导致 image_pull 路径死循环

image_pull 路径下，decision_node 给 confidence=0.5（PodStatus+KubernetesEvent），<0.7 触发循环。每次循环 check_image_pull → get_pod → 重复 PodStatus 证据。**测试**：5/5 mock 场景通过
