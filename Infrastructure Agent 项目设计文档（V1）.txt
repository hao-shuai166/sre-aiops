# Infrastructure Agent 项目设计文档（V1）

## 1. 项目背景

### 1.1 项目名称

Infrastructure Agent

### 1.2 项目定位

Infrastructure Agent 是一个面向企业级 SRE 场景的 AI 运维智能体平台。

目标不是简单实现一个聊天机器人，而是将 SRE 的故障排查经验通过：

* LLM
* Workflow
* MCP Tool
* Observability 数据
* Infrastructure API

进行结构化沉淀，使 AI 能够完成基础设施诊断、根因分析和辅助运维。

---

# 2. 项目目标

## V1 目标

实现 Kubernetes 场景下的智能故障诊断 Agent。

第一个 MVP 场景：

> 用户输入一个 Kubernetes Pod 异常问题，Agent 自动完成分析并输出 RCA（Root Cause Analysis）。

示例：

用户：

```
为什么 nginx-xxx Pod 一直 CrashLoopBackOff？
```

Agent：

自动执行：

1. 获取 Pod 状态
2. 获取 Container 状态
3. 查询 Kubernetes Events
4. 获取 Pod Logs
5. 分析异常原因
6. 输出故障原因和建议方案

---

# 3. 核心设计理念

## 3.1 Evidence Driven

所有结论必须基于真实数据。

数据来源：

* Kubernetes API
* Metrics
* Logs
* Trace
* Events

禁止：

LLM 根据经验直接猜测。

---

## 3.2 Workflow is Knowledge

Workflow 代表 SRE 的排障经验。

例如：

CrashLoopBackOff:

```
Pod Status

↓

Container Status

↓

Events

↓

Logs

↓

Image

↓

Resource

↓

Root Cause
```

Workflow 是项目最核心的资产。

---

## 3.3 Tool First

所有基础设施能力必须通过 Tool 暴露。

例如：

不要：

```
Workflow直接调用kubectl
```

而应该：

```
Workflow

↓

Tool

↓

Kubernetes API
```

# 7. 核心模块设计

## 7.1 Domain Layer

领域对象。

第一阶段：

```
Kubernetes Domain

├── Pod
├── Node
├── Deployment
└── Event
```

Domain 描述：

"我们处理什么对象"

不是：

"如何调用 API"

---

## 7.2 Workflow Layer

负责定义排障流程。

例如：

```
CrashLoopBackOff Workflow

Input:

namespace
pod_name


Process:

1. Get Pod Status

2. Get Container Status

3. Query Events

4. Query Logs

5. Analyze


Output:

Root Cause Report
```

---

## 7.3 Tool Layer

提供基础能力。

例如：

Pod Tool:

```
describe_pod()

get_pod_logs()

get_pod_events()

get_container_status()
```

---

## 7.4 Agent Layer

负责：

* 理解用户意图
* 选择 Workflow
* 调用 Tool
* 汇总结果

# 10. 开发原则

所有新增功能必须回答：

1. 它属于哪个 Domain？
2. 它属于哪个 Workflow？
3. 它需要哪些 Tool？
4. 数据来源是什么？
5. 如何验证结果正确？

---

# 11. 当前第一个开发任务

不要直接开发完整 Agent。

首先完成：

## Pod Diagnosis Workflow Design

输出：

* Workflow 流程图
* Tool 列表
* 输入输出定义
* RCA 输出格式

然后再开始代码实现。
