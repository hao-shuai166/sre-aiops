# ADR-0001: Infrastructure Agent V1 技术选型与架构设计

- **状态**: 已接受
- **日期**: 2026-07-22
- **决策者**: Infrastructure Agent Team

---

## 背景

Infrastructure Agent 的目标是构建一个 AI Native 的基础设施运维平台。V1 阶段聚焦于 Kubernetes Pod 故障的智能诊断与根因分析（RCA）。需要确定编程语言、Workflow 引擎、LLM 集成方式、工具抽象层等核心技术选型及整体架构模式。

## 决策

### 1. 使用 Python 3.12+ 作为主力语言

**理由**:
- AI/LLM 生态最为成熟（LangGraph、OpenAI SDK、MCP SDK 均以 Python 为第一支持语言）
- kubernetes-python-client 是 K8s 官方维护的客户端库，功能完整
- 团队在 Python 生态有较多积累
- Python 3.12 提供了显著的解释器性能提升和更好的类型系统支持

### 2. 使用 LangGraph 作为 Workflow 引擎

**理由**:
- 原生支持有状态、多步骤 Agent Workflow
- Graph-based 建模天然适合 SRE 排障流程的分支和回退逻辑
- 与 LLM 深度集成，支持 Tool Calling
- 社区活跃，LangChain 生态完备

**备选方案评估**:
- Temporal / Prefect: 偏重任务编排，非 AI Workflow 最佳选择
- 自研 Workflow: 开发成本高，重复造轮子

### 3. 使用 MCP (Model Context Protocol) 作为 Tool 抽象层

**理由**:
- 标准化 Tool 接口，LLM 可动态发现和调用
- 与 Workflow 解耦，Tool 可独立测试和演进
- 支持未来扩展：Metrics、Logs、Trace 等数据源均可通过 MCP Tool 接入
- Anthropic 主推的开放协议，生态兼容性好

### 4. 分层架构：Agent → Workflow → Tool → Adapter → Infrastructure

**理由**:
- 每层职责清晰，符合单一职责原则
- Tool 层隔离了 Workflow 与底层基础设施的耦合
- Adapter 层支持未来多基础设施后端（Kubernetes、Prometheus、Loki 等）的统一接入

### 5. Evidence Driven 设计原则

**理由**:
- 所有诊断结论必须基于可追溯的真实数据（K8s API、Metrics、Logs、Events）
- 禁止 LLM 基于"经验"直接猜测，避免幻觉导致错误运维操作
- 每条诊断结果均可追溯到具体的数据源

### 6. Workflow is Knowledge 设计原则

**理由**:
- SRE 排障经验通过 Workflow 结构化沉淀，而非散落在文档中
- Workflow 可复用、可测试、可组合
- 每个故障场景（CrashLoopBackOff、OOMKilled、ImagePullBackOff 等）对应一个独立 Workflow

## 后果

### 正面影响

- 清晰的分层架构降低了各模块耦合度，便于独立开发和测试
- MCP 标准化 Tool 接口使未来扩展新数据源变得简单
- LangGraph 为复杂排障流程提供了良好的建模能力
- Python 生态保证了 AI 相关能力的快速集成

### 需要关注的方面

- LangGraph 在复杂 Workflow 场景下的调试和可观测性需要额外投入
- Python 的 GIL 在高并发场景下可能成为瓶颈，后续需评估 asyncio 或 FastAPI 的多 worker 部署
- MCP 协议仍在快速迭代中，需要注意 SDK 版本兼容性
